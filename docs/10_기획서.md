# 10. 기획서 — 소규모 창고 재고관리 시스템

> Phase 1 산출물. "무엇을, 누구를 위해, 어디까지 만들지"를 정한 문서입니다.
> 작성일: 2026-11-20 / 상태: 초안(사용자 확인 필요)

## 1. 한 줄 정의

> **소규모 창고의 품목·입출고·재고를 관리하고, 직원 계정과 권한을 관리하는 웹 시스템**

## 2. 배경 (가상의 상황)

- 직원 5명 규모의 작은 창고. 지금은 **엑셀 파일 하나**로 재고를 관리한다.
- 문제: 여러 명이 동시에 고치면 숫자가 어긋나고, 누가 언제 뺐는지 기록이 없다.
- 그래서 **웹으로 같이 보는 재고 시스템**을 만든다.

## 3. 만들 범위 — 2단계로 나눠서 진행

| 단계 | 모듈 | 하는 일 | 해당 Phase |
|---|---|---|---|
| 1단계 | **재고관리** | 품목 등록, 입고/출고, 현재고 조회, 이력 조회 | Phase 4 |
| 2단계 | **사용자관리** | 계정 생성, 로그인, 역할(권한), 세션/토큰 관리 | Phase 5·6·8 |

> 1단계는 **로그인 없이** 먼저 만든다. 서버↔DB 대화에 집중하기 위해서다.
> 2단계에서 로그인을 붙이고, 그때 **세션·쿠키·토큰**을 직접 비교하며 실습한다.

## 4. 사용자(역할) 정의

| 역할 | 누구 | 할 수 있는 일 |
|---|---|---|
| **관리자 (admin)** | 창고 책임자 | 재고 기능 전부 + 품목 삭제 + **직원 계정 생성·비활성화·역할 변경** |
| **직원 (staff)** | 창고 작업자 | 품목 조회·등록, 입고/출고 등록, 이력 조회 (삭제·계정관리 불가) |

> 권한 검사는 **화면이 아니라 서버에서** 한다. (화면에서 버튼만 숨기는 건 보안이 아니다 — Phase 8)

## 5. 기능 요구사항

### 5-1. 재고관리 (1단계)

| ID | 기능 | 설명 | MVP |
|---|---|---|---|
| F-01 | 품목 등록 | 품목코드·이름·단위·안전재고 입력 | ✅ |
| F-02 | 품목 목록/검색 | 이름·코드로 검색, 현재고 함께 표시 | ✅ |
| F-03 | 품목 수정 | 이름·단위·안전재고 변경 (품목코드는 변경 불가) | ✅ |
| F-04 | 품목 삭제 | 관리자만. 입출고 이력이 있으면 삭제 대신 **사용중지** | ⬜ 나중 |
| F-05 | 입고 등록 | 품목·수량·메모 → 재고 **증가** | ✅ |
| F-06 | 출고 등록 | 품목·수량·메모 → 재고 **감소**, 재고보다 많이 출고 불가 | ✅ |
| F-07 | 입출고 이력 조회 | 날짜·품목으로 필터 | ✅ |
| F-08 | 안전재고 경고 | 현재고 < 안전재고인 품목을 목록에서 표시 | ⬜ 나중 |
| F-09 | 재고 실사(조정) | 실제 수량과 차이 날 때 수량 보정 + 사유 기록 | ⬜ 나중 |
| F-10 | 엑셀 내보내기 | 재고 목록 CSV 다운로드 | ⬜ 나중 |

### 5-2. 사용자관리 (2단계)

| ID | 기능 | 설명 | MVP |
|---|---|---|---|
| U-01 | 로그인 / 로그아웃 | 아이디·비밀번호 → 인증 성공 시 세션 또는 토큰 발급 | ✅ |
| U-02 | 내 정보 조회 | 로그인한 사용자 정보 확인 | ✅ |
| U-03 | 계정 생성 | **관리자만** 직원 계정을 만든다 (공개 회원가입 없음) | ✅ |
| U-04 | 사용자 목록 조회 | 관리자만 | ✅ |
| U-05 | 역할 변경 / 계정 비활성화 | 관리자만. 계정은 삭제하지 않고 비활성화 | ✅ |
| U-06 | 비밀번호 변경 | 본인이 변경 (현재 비밀번호 확인 후) | ✅ |
| U-07 | 로그인 실패 횟수 제한 | 연속 실패 시 일정 시간 차단 | ⬜ Phase 8 |
| U-08 | 접속 기록(감사 로그) | 누가 언제 로그인했는지 기록 | ⬜ 나중 |

> 🤝 **U-03 결정**: 창고 직원용 사내 시스템이므로 **공개 회원가입은 만들지 않는다**.
> (Phase 5에서 다시 확인)

## 6. 비기능 요구사항

| 구분 | 요구사항 |
|---|---|
| 보안 | 모든 SQL은 파라미터 바인딩 / 입력값은 서버에서 정규식 검증 / 비밀번호는 bcrypt 해시 / 비밀값은 `.env` |
| 보안 | 권한 검사는 서버에서 / 에러 응답에 내부 정보(SQL·스택) 노출 금지 |
| 성능 | 품목 1,000건·이력 10만건 기준으로 목록 조회 1초 이내 |
| 정확성 | 입출고는 **트랜잭션**으로 처리 — 이력 기록과 재고 증감이 **함께 성공하거나 함께 실패** |
| 운영 | DB 정기 백업(Phase 12), 서버 3대 분리 배포(Phase 11) |
| 사용성 | PC 브라우저 기준(크롬). 모바일 대응은 범위 밖 |

## 7. 화면 목록

| 화면 | 경로 | 설명 | 접근 |
|---|---|---|---|
| 로그인 | `/login` | 아이디·비밀번호 입력 | 누구나 |
| 품목 목록 | `/items` | 검색 + 현재고 표시, 첫 화면 | 로그인 |
| 품목 등록/수정 | `/items/new`, `/items/:id` | 품목 정보 입력 폼 | 로그인 |
| 입출고 등록 | `/transactions/new` | 품목 선택 + 입고/출고 + 수량 | 로그인 |
| 입출고 이력 | `/transactions` | 날짜·품목 필터 | 로그인 |
| 사용자 관리 | `/users` | 계정 생성·역할 변경·비활성화 | 관리자만 |

## 9. 이번 프로젝트에서 **안 하는 것** (Out of Scope)

- 구매/발주, 판매/주문, 회계, 급여
- 바코드 스캐너 연동, 모바일 앱
- 다중 창고(창고가 여러 개인 경우) — 창고는 한 곳으로 가정
- 비밀번호 찾기(이메일 발송)

## 10. 이 문서에서 나온 용어

| 용어 | 설명 |
|---|---|
| 요구사항 | 시스템이 **무엇을 해야 하는가**를 적은 목록. 기능 요구사항(무슨 일을 하나) / 비기능 요구사항(얼마나 빠르고 안전한가)으로 나뉨 |
| MVP | Minimum Viable Product. **일단 이것만 되면 쓸 수 있는** 최소 기능 묶음. 나머지는 뒤로 미룸 |
| 유스케이스 | "누가(역할) → 무엇을 한다"로 쓴 사용 시나리오. 예: *직원이 출고를 등록한다* |
| 와이어프레임 | 화면의 **뼈대 그림**. 색·디자인 없이 "무엇이 어디에 있는지"만 그림 |
| Out of Scope | 이번에 **만들지 않기로 정한 것**. 적어두지 않으면 범위가 계속 늘어남 |
