# 00. 용어 바로잡기 — 처음 요청을 정확한 말로 다시 정리

처음에 말씀하신 내용을 정확한 용어로 바꿔서 다시 정리했습니다.
틀린 게 아니라 **"실무에서는 이렇게 부른다"**는 정도로 보시면 됩니다.

---

## 1. "서버"라는 말의 두 가지 뜻

"서버"는 두 가지 의미가 섞여 쓰입니다. 처음 요청에는 **두 의미가 모두** 들어 있었습니다.

| 구분 | 뜻 | 예시 | 우리 프로젝트 |
|---|---|---|---|
| **① 서버 컴퓨터** (물리/가상 서버) | 프로그램이 돌아가는 **기계** | 데이터센터의 서버 장비, 클라우드에서 빌린 가상 서버 | **클라우드 서버 3대** (후반에 적용) |
| **② 서버 프로그램 = 서비스** | 그 기계 위에서 돌아가며 요청에 응답하는 **프로그램** | 로그인 담당 `auth-service`, 업무 담당 `erp-service` | 서비스 3개 + PostgreSQL |

> 🏠 **비유**: 서버 컴퓨터는 **건물**, 서비스는 건물 안의 **가게**입니다.
> 건물 한 채에 가게 여러 개가 들어갈 수도 있고(개발 단계 — 내 PC 한 대),
> 가게마다 건물을 따로 쓸 수도 있습니다(운영 단계 — 서버 3대).

**클라이언트**는 서버에 **요청을 보내는 쪽**입니다. 우리 프로젝트에서는 브라우저에서 돌아가는 **React 화면**이 클라이언트입니다.
화면 쪽을 **프론트엔드**, 서버 쪽을 **백엔드**라고도 합니다.

## 2. "서버는 2~3개로 분리 (IAM 서버, DB 서버, 게이트웨이)"

### 2-1. 각 이름 바로잡기

| 처음 표현 | 바로잡은 표현 | 설명 |
|---|---|---|
| IAM 서버 | **인증 서비스 (auth-service)** | IAM(Identity and Access Management)은 "누가 무엇에 접근할 수 있는지 관리하는" **개념/분야**의 이름입니다. 이를 실제로 담당하는 프로그램은 보통 *인증 서버*, *Auth 서버*라고 부릅니다. (AWS IAM, Keycloak 같은 제품도 있지만 우리는 직접 만듭니다.) |
| DB 서버 | **DB 서버 (PostgreSQL)** | 표현은 맞습니다. 다만 DB 프로그램은 **코드로 만드는 게 아니라 설치해서 쓰는** 프로그램입니다. 우리가 만드는 건 DB에 데이터를 넣고 꺼내는 **API 서비스**입니다. |
| 게이트웨이 | **API 게이트웨이 (gateway)** | 맞습니다. 클라이언트가 접속하는 **단 하나의 입구**입니다. 요청을 알맞은 서비스로 전달(라우팅)하고, 로그인한 사용자인지 검사하는 **검문소** 역할을 합니다. |
| (빠진 것) | **업무 서비스 (erp-service)** | 실제 ERP 기능(품목, 재고, 거래처 등)을 처리하는 서비스가 하나 더 필요합니다. |

### 2-2. 서버를 물리적으로 나누는 게 불필요한가? → **아니요, 실무에서는 일반적입니다**

서버(기계)를 나누면 얻는 것:

| 얻는 것 | 설명 |
|---|---|
| **장애 격리** | 한 서버가 죽어도 **피해가 그 서버에만** 머뭅니다. 예: 앱 서버가 메모리 부족으로 멈춰도 DB 데이터는 안전 |
| **보안 분리** | DB 서버를 인터넷에서 **아예 안 보이게** 숨길 수 있습니다. 외부엔 게이트웨이만 노출 |
| **자원 분리** | 무거운 작업이 DB의 CPU/메모리를 뺏지 않음 |
| **독립적 확장·관리** | 바쁜 서버만 키우거나, 한 서버만 점검/재시작 가능 |

⚠️ **하지만 꼭 알아둘 점**: 서버를 나누는 것만으로는 "장애가 나도 서비스가 계속 돈다"가 되지 않습니다.

```
 [서버1: 게이트웨이] → [서버2: 서비스들] → [서버3: DB]
                                            💥 DB 서버가 죽으면?
                                            → 데이터는 지켜져도(백업이 있다면) 서비스는 멈춤
```

이렇게 **하나가 죽으면 전체가 멈추는 지점**을 **단일 장애점(SPOF)** 이라고 합니다. 대응 방법은 세 가지 수준이 있습니다.

| 수준 | 방법 | 효과 | 이번 프로젝트 |
|---|---|---|---|
| 1. **장애 격리** | 서버 분리 | 피해 범위 축소, 보안 향상 | ✅ 실습 |
| 2. **백업·복구** | 정기 백업을 **다른 서버/저장소**에 보관하고 복구 훈련 | 데이터 손실 방지, 빠른 복구 | ✅ 실습 |
| 3. **이중화 (고가용성)** | 같은 서버를 2대 이상 두고 하나가 죽으면 다른 쪽이 넘겨받음 | 거의 무중단 | ❌ 개념만 (난이도·비용 큼) |

> 💡 백업을 **같은 서버에** 두면 그 서버가 죽을 때 백업도 같이 사라집니다. 백업은 반드시 **다른 곳에** 보관해야 합니다.

### 2-3. 우리 프로젝트의 서버 배치 (기본안 — Phase 2에서 확정)

```
                 인터넷
                   │  (80/443 포트만 열림)
       ┌───────────▼────────────┐
       │ 서버1: 웹/게이트웨이 서버 │  ← 유일하게 외부에 공개
       │  - React 화면 파일       │
       │  - API Gateway           │
       └───────────┬────────────┘
                   │  내부망(사설 IP)
       ┌───────────▼────────────┐
       │ 서버2: 애플리케이션 서버  │  ← 외부 접근 차단
       │  - auth-service (IAM)    │
       │  - erp-service           │
       └───────────┬────────────┘
                   │  내부망, 5432 포트는 서버2에게만 허용
       ┌───────────▼────────────┐
       │ 서버3: DB 서버           │  ← 외부 접근 차단
       │  - PostgreSQL            │
       │  - 백업 → 외부 저장소로   │
       └────────────────────────┘
```

> 🤝 auth-service(IAM)를 erp-service와 다른 서버에 따로 둘지는 Phase 2 설계 때 함께 정합니다.
> 서버는 **클라우드 무료 범위 안에서** 빌리고, 앱이 내 PC에서 다 동작한 뒤(Phase 11)에 옮깁니다.

## 3. "보안 등의 인증을 거쳐서 웹서비스를 이용"

보안에서는 아래 두 단어를 꼭 구분합니다.

| 용어 | 질문 | 예시 |
|---|---|---|
| **인증 (Authentication)** | "너 **누구**야?" | 아이디/비밀번호로 로그인 |
| **인가 (Authorization)** | "너 이거 **해도 돼**?" | 관리자만 품목을 삭제할 수 있음 |

우리 프로젝트에서는 로그인하면 **토큰(JWT)** 이라는 "출입증"을 발급받고,
이후 모든 요청에 출입증을 붙여 보내면 게이트웨이가 확인하는 방식으로 만듭니다.

## 4. "아이템선정, 시스템구성도, 아키텍처, 기획, 설계"

| 처음 표현 | 정확한 의미 | 결과물 |
|---|---|---|
| 아이템 선정 | **주제 선정 / 범위 정의** — 무엇을 만들지, 어디까지 만들지 정하기 | 한 줄 정의, 기능 목록 |
| 기획 | **무엇을(What)** 만들지 정하는 단계 — 누가 쓰고, 어떤 기능과 화면이 필요한지 | 요구사항 정의서, 화면 목록, 와이어프레임 |
| 아키텍처 | 시스템을 **어떤 큰 덩어리로 나누고 어떻게 연결할지**에 대한 구조적 결정 | 아키텍처 결정 기록 |
| 시스템 구성도 | 아키텍처를 **그림으로 표현한 것**. 보통 두 종류를 그립니다: **소프트웨어 구성도**(서비스 간 연결)와 **인프라 구성도**(서버·네트워크 배치) | 구성도 다이어그램 |
| 설계 | **어떻게(How)** 만들지 구체화 — DB 표 구조, API 목록, 인증 흐름, 서버 배치 | ERD, API 명세서, 시퀀스 다이어그램, 인프라 구성도 |

> 순서: **주제 선정 → 기획 → 아키텍처/구성도 → 상세 설계 → 개발 → 테스트 → 배포(서버 분리) → 운영(백업·장애 대응)**

## 5. "웹 ERP"

- **ERP (Enterprise Resource Planning, 전사적 자원 관리)**: 회사의 구매·판매·재고·회계·인사 등을 하나의 시스템에서 관리하는 프로그램.
- 실제 ERP는 거대하므로, 우리는 **1~2개 모듈만** 골라 작게 만듭니다. (어떤 모듈을 할지는 Phase 1에서 함께 정합니다.)
- **웹 ERP**: 프로그램 설치 없이 **브라우저로 접속해서 쓰는** ERP.

---

## ✍️ 다시 정리한 요청 (정확한 용어 버전)

> JavaScript(Node.js + React)로 **간단한 웹 ERP**를 만들며 웹 개발 전 과정을 배우고 싶다.
> **주제 선정 → 기획 → 아키텍처 설계(시스템 구성도) → 상세 설계(DB·API) → 개발 → 테스트 → 배포 → 운영**까지 경험한다.
>
> - **소프트웨어 구성**: **API 게이트웨이, 인증 서비스(auth-service), 업무 서비스(erp-service)** 3개 백엔드 서비스 + **PostgreSQL** + **React 클라이언트**
> - **인프라 구성**: 장애 격리와 보안을 위해 **클라우드 서버 3대(웹/게이트웨이 · 애플리케이션 · DB)** 로 물리적으로 분리하고, DB는 외부에서 접근할 수 없게 한다.
> - **장애 대비**: DB를 **다른 저장소에 정기 백업**하고 **복구 훈련**을 하며, 서버 하나를 꺼서 장애가 어디까지 번지는지 확인한다.
> - **보안**: 사용자는 **로그인(인증)** 후 **권한(인가)** 에 맞는 기능만 이용하며, 입력 검증(정규식)과 SQL 인젝션 방어를 처음부터 적용한다.
