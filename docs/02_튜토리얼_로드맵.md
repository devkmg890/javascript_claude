# 02. 튜토리얼 로드맵

> 전체 여정을 **Phase 0 ~ 12**로 나눴습니다. 한 Phase는 보통 1~3회 세션 분량입니다.
> 각 Phase를 시작할 때 Claude가 `docs/phases/phaseN_*.md`에 **상세 실습 가이드**를 만들어 함께 진행합니다.
> 🤝 표시는 **진행 전에 사용자와 상의해서 정할 항목**입니다.

---

## 🗺️ 전체 흐름

```
[준비]  Phase 0  개발 환경 준비
[기획]  Phase 1  주제 선정 & 기획
[설계]  Phase 2  아키텍처 & 상세 설계
[개발]  Phase 3  Node.js 기초 워밍업
        Phase 4  erp-service (업무 API + DB)
        Phase 5  auth-service (회원가입·로그인·JWT)
        Phase 6  API Gateway (입구·인증 검사)
        Phase 7  React 클라이언트
        Phase 8  권한(인가) & 보안 강화
[품질]  Phase 9  테스트 & 로깅
[배포]  Phase 10 배포 준비 (Linux · 운영 설정 · Docker)
        Phase 11 클라우드 서버 3대로 분리 배포
[운영]  Phase 12 백업 · 복구 · 장애 격리 훈련 & 회고
```

> 🏢 **서버 분리 전략**: 설계(Phase 2)는 처음부터 **서버 3대 기준**으로 하고,
> 개발(Phase 3~9)은 **내 PC 한 대**에서 편하게 한 뒤, 앱이 다 동작하면 **클라우드 서버 3대**로 나눠 올립니다(Phase 11).
> 이렇게 하면 문제가 생겼을 때 "코드 문제"인지 "서버/네트워크 문제"인지 구분하기 쉽습니다.
> 코드에서 서버 주소를 `.env`로 빼두는 습관만 지키면, 옮길 때 코드는 거의 바꾸지 않아도 됩니다.

> 💡 **왜 이 순서인가?**
> 업무 API(Phase 4)를 먼저 만들어 "서버가 DB와 대화하는 법"을 익히고,
> 그다음 인증(5) → 입구(6) → 화면(7) 순으로 **안쪽에서 바깥쪽으로** 쌓아갑니다.
> 한 번에 다 연결하지 않으니 문제가 생겨도 원인을 찾기 쉽습니다.

## 🛡️ 보안 원칙 — 처음부터 끝까지 적용

보안은 마지막에 "덧붙이는" 것이 아니라 **코드를 처음 쓸 때부터 습관**으로 넣습니다.
아래 항목은 각 Phase에 나눠서 실습하며, 🛡️ 표시로 구분합니다.

| 위협/주제 | 방어 방법 | 적용 Phase |
|---|---|---|
| **SQL 인젝션** | SQL에 값을 문자열로 이어붙이지 않고 **파라미터 바인딩**(`$1`, `$2`) 사용 | 4부터 계속 |
| **잘못된 입력** | **정규식** + 검증 규칙으로 입력값 형식·길이·범위 검사 (화이트리스트 방식) | 4, 5, 7 |
| **비밀번호 유출** | bcrypt 해시 저장, 비밀번호 정책(정규식), 평문 로그 금지 | 5 |
| **토큰 위조/탈취** | JWT 서명 검증, 짧은 만료시간, 비밀키는 `.env`에 | 5, 6, 8 |
| **무차별 대입 공격** | 로그인 시도 횟수 제한 (rate limit) | 6, 8 |
| **XSS** | React의 자동 이스케이프 활용, `dangerouslySetInnerHTML` 금지, 입력 검증 | 7, 8 |
| **CSRF** | 토큰 저장 방식에 따라 대응 (쿠키 사용 시 SameSite 등) | 7, 8 |
| **보안 설정** | `helmet`(보안 헤더), CORS 허용 목록, 에러 메시지에 내부정보 숨기기, `.gitignore`로 비밀값 보호 | 4, 6, 8 |
| **권한 우회** | 화면이 아니라 **서버에서** 권한 검사 (RBAC) | 6, 8 |
| **의존성 취약점** | `npm audit`으로 패키지 취약점 점검 | 8, 9 |
| **서버 노출** | 게이트웨이 서버만 공개, 앱·DB 서버는 내부망 전용, 방화벽(보안 그룹)으로 필요한 포트만 허용 | 2, 11 |
| **서버 접속 탈취** | SSH 비밀번호 로그인 끄고 **SSH 키**만 허용, root 직접 로그인 금지 | 11 |
| **통신 도청** | HTTPS 적용 (무료 인증서) | 11 |
| **데이터 손실** | DB 정기 백업을 **다른 저장소**에 보관, 복구 훈련 | 12 |

> 🧪 각 방어는 **"공격 → 막히는 것 확인"** 순서로 실습합니다.
> 예: 일부러 취약한 코드로 SQL 인젝션이 성공하는 걸 본 뒤, 파라미터 바인딩으로 고쳐서 막히는 걸 확인.
> (실습은 **내 PC의 내 프로젝트에서만** 합니다. 남의 서비스에 시도하면 불법입니다.)

## Phase 2. 아키텍처 & 상세 설계

## Phase 4. erp-service — 업무 API + DB
**목표**: Express로 CRUD API를 만들고 PostgreSQL에 저장한다. (아직 로그인 없음)

- [ ] `services/erp-service` 프로젝트 생성 (`npm init`, express 설치)
- [ ] 폴더 구조 잡기 (routes / controllers / db)
- [ ] `.env`로 DB 접속 정보 분리
- [ ] `erp_db` 생성 및 테이블 생성 SQL 작성
- [ ] 핵심 엔티티 CRUD API 구현 (예: 품목 등록/조회/수정/삭제)
- [ ] 업무 로직 하나 구현 (예: 입고/출고 시 재고 증감 — **트랜잭션** 사용)
- [ ] 에러 응답 형식 통일 — 🛡️ 사용자에게는 일반 메시지만, 상세 에러(스택·SQL)는 서버 로그에만
- [ ] API 테스트 도구로 확인 (🤝 VS Code REST Client / Postman / Thunder Client)
- [ ] 🛡️ **SQL 인젝션 실습**: 문자열 이어붙이기로 만든 취약한 조회 API에 `' OR '1'='1` 공격 → 전체 데이터 노출 확인 → **파라미터 바인딩**으로 수정 → 막히는 것 확인
- [ ] 🛡️ **정규식 기초**: `^ $ [] {} + * ? \d \w` 의미, `RegExp.test()` 사용법, regex101.com에서 연습
- [ ] 🛡️ **입력값 검증 미들웨어**: 품목코드(예: `^[A-Z]{2}\d{4}$`), 수량(양의 정수), 문자열 길이 제한 등
- [ ] 🛡️ 정규식 주의점: 너무 복잡한 정규식은 서버를 멈추게 할 수 있음(**ReDoS**) — 길이 먼저 제한하기
- [ ] 🛡️ `.gitignore`에 `.env`, `node_modules` 추가, `.env.example`만 공유
- [ ] 🛡️ DB 접속 계정을 슈퍼유저 말고 **서비스 전용 계정**(필요한 권한만)으로 사용 — 최소 권한 원칙
- 🤝 검증 방식: 정규식 직접 작성 vs 검증 라이브러리(zod, express-validator) — 기본안은 **직접 작성으로 원리 학습 → 이후 라이브러리로 교체**

**배울 용어**: Express, 미들웨어, CRUD, SQL, 트랜잭션, 환경변수, 상태 코드, SQL 인젝션, 파라미터 바인딩, 정규식, 입력 검증, ReDoS, 최소 권한 원칙

## Phase 5. auth-service — 회원가입 · 로그인 · JWT
**목표**: 인증을 전담하는 서비스를 따로 만든다.

- [ ] `services/auth-service` 생성, `auth_db` 및 `users` 테이블
- [ ] 회원가입 API — 비밀번호는 **bcrypt 해시**로 저장
- [ ] 로그인 API — 성공 시 **JWT(Access Token)** 발급
- [ ] 내 정보 조회 API (토큰 검증 연습)
- [ ] 사용자 역할(role) 컬럼 추가 (관리자/직원)
- [ ] 🛡️ 정규식으로 검증: 아이디(영문·숫자 4~20자), 이메일 형식, **비밀번호 정책**(8자 이상 + 영문/숫자/특수문자 조합)
- [ ] 🛡️ 로그인 실패 메시지는 "아이디 또는 비밀번호가 틀렸습니다"로 통일 (어느 쪽이 틀렸는지 알려주지 않기)
- [ ] 🛡️ JWT 비밀키는 길고 무작위로 생성해 `.env`에 보관, 만료시간 설정(예: 15분)
- [ ] 🛡️ 비밀번호·토큰이 로그에 찍히지 않는지 확인
- 🤝 회원가입을 누구나 할 수 있게 할지, 관리자만 계정을 만들지

**배울 용어**: 인증, 해시, bcrypt, 솔트, JWT, 토큰, 비밀 키(secret), 비밀번호 정책

## Phase 6. API Gateway — 단일 입구 & 인증 검사
**목표**: 클라이언트는 게이트웨이 하나만 알면 되도록 만든다.

- [ ] `services/gateway` 생성 (포트 8000)
- [ ] `/api/auth/*` → auth-service, `/api/erp/*` → erp-service 로 **프록시** 연결
- [ ] JWT 검사 미들웨어: 로그인 안 한 요청은 `401`로 차단
- [ ] 검증된 사용자 정보를 뒤쪽 서비스로 전달 (헤더)
- [ ] 🛡️ CORS 설정 — `*`(전체 허용) 금지, React 개발 서버 주소만 **허용 목록**에
- [ ] 🛡️ `helmet`으로 보안 헤더 일괄 적용, `X-Powered-By` 헤더 숨기기
- [ ] 🛡️ 요청 본문 크기 제한 (예: 100kb) — 거대한 요청으로 서버 마비 방지
- [ ] 🛡️ 로그인 API에 **rate limit** (예: 1분에 5회) — 무차별 대입 공격 방지
- [ ] 🛡️ 뒤쪽 서비스(8001, 8002)는 게이트웨이를 통해서만 접근하도록 설정 (외부 직접 접근 차단 개념)
- [ ] 요청 로그 남기기
- [ ] 3개 서비스 동시 실행 방법 정리 (터미널 여러 개 / 🤝 `concurrently` 같은 도구)

**배울 용어**: API 게이트웨이, 프록시, CORS, 미들웨어 체인

## Phase 7. React 클라이언트
**목표**: 브라우저에서 로그인하고 ERP 기능을 사용하는 화면을 만든다.

- [ ] Vite로 `web` 프로젝트 생성, 폴더 구조 이해
- [ ] React 기초: 컴포넌트, JSX, props, state(`useState`), `useEffect`
- [ ] React Router로 화면 이동 (로그인 / 목록 / 등록 / 상세)
- [ ] 로그인 화면 → 토큰 저장 → API 호출 시 토큰 첨부
- [ ] 목록 화면(표), 등록/수정 폼, 삭제
- [ ] 로그인 안 했으면 로그인 화면으로 보내기
- [ ] 🛡️ 폼 입력값을 **서버와 같은 정규식**으로 미리 검사 (사용자 편의용 — 진짜 검사는 여전히 서버)
- [ ] 🛡️ **XSS 실습**: 품목명에 `<script>` 넣어보기 → React가 자동으로 막는 원리 확인, `dangerouslySetInnerHTML`이 위험한 이유
- 🤝 토큰 저장 위치 (localStorage vs 쿠키) — 장단점 설명 후 결정
- 🤝 UI 스타일 방법 (순수 CSS / UI 라이브러리)

**배울 용어**: React, Vite, 컴포넌트, JSX, state, props, Hook, SPA, 라우터

- [ ] 🛡️ 권한 우회 실습: 직원 계정 토큰으로 관리자 API를 직접 호출 → `403`으로 막히는지 확인
- [ ] 🛡️ 남의 데이터 접근 막기 (URL의 id만 바꿔서 조회하는 공격 — IDOR)
- [ ] 🛡️ CSRF 개념과 대응 (Phase 7에서 정한 토큰 저장 방식 기준)
- [ ] 🛡️ 계정 잠금: 로그인 N회 실패 시 일정 시간 잠금
- [ ] 🛡️ 감사 로그(Audit Log): 누가 언제 무엇을 바꿨는지 기록 — ERP에서 특히 중요
- [ ] 🛡️ `npm audit`으로 패키지 취약점 점검
- [ ] 🛡️ **보안 점검 체크리스트** 작성 및 전체 서비스 점검 (`docs/30_보안점검.md`)

**배울 용어**: 인가, RBAC, Refresh Token, XSS, CSRF, IDOR, 감사 로그, OWASP Top 10

## Phase 11. 클라우드 서버 3대로 분리 배포
**목표**: 서버를 물리적으로 나눠 실제 운영 환경처럼 배포한다. (**무료 범위 안에서**)

- [ ] 🤝 클라우드 업체 선택 — 서버 3대를 **무료로** 운영할 수 있는 곳 비교 (진행 시점의 무료 정책을 함께 확인)
- [ ] 클라우드 가입 — ⚠️ 카드 등록·본인인증은 **사용자가 직접**, **요금 알림(예산 경보)** 설정 필수
- [ ] 내부망(VPC/서브넷) 만들기, 서버 3대 생성 (Ubuntu)
- [ ] 🛡️ SSH 키로 접속, 비밀번호 로그인·root 로그인 끄기
- [ ] 🛡️ 방화벽(보안 그룹) 규칙
  - 서버1: 80/443만 인터넷에 공개, SSH는 내 IP만
  - 서버2: 서버1에서 오는 8001/8002만 허용
  - 서버3: 서버2에서 오는 5432만 허용
- [ ] 서버3에 PostgreSQL 설치, 서비스 전용 계정 생성
- [ ] 서버2에 auth-service·erp-service, 서버1에 Nginx + 게이트웨이 + React 빌드 배포
- [ ] 🛡️ 도메인(🤝 무료/유료) 연결 및 HTTPS 적용
- [ ] 외부에서 접속 테스트 + **서버2·3에 외부에서 직접 접속이 안 되는지** 확인

**배울 용어**: 클라우드, 인스턴스, 프리티어, VPC, 서브넷, 공인/사설 IP, 보안 그룹, SSH 키, Nginx, 리버스 프록시, HTTPS

## Phase 12. 백업 · 복구 · 장애 격리 훈련 & 회고
**목표**: "서버가 죽어도 데이터는 지키고, 어디까지 영향이 가는지 안다."

- [ ] `pg_dump`로 DB 백업 → **서버3 밖의 저장소**(다른 서버 또는 클라우드 저장소)로 보관
- [ ] 백업 자동화 (cron으로 매일 실행) + 오래된 백업 정리
- [ ] **복구 훈련**: 새 DB에 백업을 되살려 데이터 확인 ("복구해보지 않은 백업은 백업이 아니다")
- [ ] **장애 격리 훈련**: 서버를 하나씩 꺼보고 결과 기록
  - 서버2를 끄면? → 게이트웨이가 적절한 에러(503)를 주는지, 화면이 안내 메시지를 보여주는지
  - 서버3을 끄면? → 서비스가 죽지 않고 에러를 반환하는지, 다시 켜면 자동으로 재연결되는지
- [ ] 헬스체크로 서버 상태 확인하는 간단한 모니터링
- [ ] 장애 대응 문서(런북) 작성: "이럴 땐 이렇게" (`docs/40_장애대응.md`)
- [ ] (개념만) 이중화·레플리케이션·로드밸런서는 어떻게 동작하는지 정리
- [ ] 회고: 잘된 점 / 어려웠던 점 / 다음에 해볼 것 (`docs/99_회고.md`)

**배울 용어**: 백업, 복구, pg_dump, cron, 장애 격리, 헬스체크, 런북, 이중화, 고가용성, 레플리케이션, 장애 조치
